## Часть 1. Наблюдаемость

### 1. Мониторинг, которого не было: 8 дней без заявок

**Проблема.** Приём заявок на сайте агентства сломался. Заметили через **восемь дней**:
заявок не было, и отличить «нет трафика» от «сломан приём» было нечем. Метрики
«сколько дней с последней заявки» не существовало - значит, и алерта быть не могло.

**Что сделал.**

- Сначала измерение, потом алерт: скрипт ходит в API CRM, считает состояние воронки
  (последний лид, открытые задачи, активность порталов) и публикует метрики в Pushgateway.
- Prometheus скрейпит их, правила лежат в `rules.yml`, применяются перезагрузкой
  через `POST /-/reload`.
- Алерты: «нет новых лидов > 3 дней, `for: 1h`» и отдельный критический порог.
- Отдельно разобрал ловушку с метрикой: счётчик нетронутых лидов построен на `modifiedAt`,
  а наши же действия (назначение ответственного, задачи) двигают дату - метрика занижает.
  Честный признак «работа не идёт» - задачи: открытые > 0 при начатых = 0.

**Результат.** Авария класса «приём заявок мёртв» видна через час, а не через неделю.

**Стек:** Python, Prometheus, Pushgateway, Alertmanager, CRM API.

### 2. Один шаблон мониторинга врал про 90 серверов

**Проблема.** В системе мониторинга на 137 хостов нашлась системная ошибка шаблона:
90 Windows-хостов отдавали **неверные события**. Алерты формально работали, а сигнал
был ложным - худший вариант: не тишина, а уверенность в том, что всё под контролем.

**Что сделал.**

- Нашёл причину на уровне шаблона, а не отдельных хостов - значит, починил один раз,
  а не 90.
- Исправил и прогнал проверку по всему парку: события стали соответствовать реальному
  состоянию.
- Выстроил гигиену вокруг: базовый профиль хоста через Ansible (chrony, auditd,
  zabbix-agent, nginx), единые политики, fail2ban с метриками и алертами на 39 хостах.
- Алертинг на неудачные SSH-входы и блокировки fail2ban по всему парку - с работой
  над ложными срабатываниями, а не «включил и забыл».

**Результат.** Мониторинг перестал врать; изменение в общем слое масштабируется на весь
парк вместо 90 ручных правок.

**Стек:** Zabbix 7.x (шаблоны, LLD, API), Ansible, Linux (REDOS 8), Windows Server,
PowerShell/Bash.

### 3. Усталость от алертов: как уменьшал шум

**Контекст.** Парк из 90 Windows-серверов и 43 Linux-хостов, дежурство на несколько
сервисов. Алерты, которые срабатывают всегда, перестают читать - а вместе с ними
перестают читать и настоящие.

**Что сделал.**

- Развёл сигналы по уровням: то, что требует действия сейчас, и то, что можно смотреть
  утром в отчёте.
- Настроил ежедневные отчёты через Zabbix API и идемпотентные скрипты вместо постоянных
  пушей в чат.
- Добился того, чтобы «сломан вход» и «кто-то ошибся паролем» не выглядели одинаково.

**Результат.** Поток ложных срабатываний сократил: настоящее событие стало видно на фоне шума, а рутина ушла в ежедневный отчёт, который читают утром, а не в три часа ночи.

**Стек:** Zabbix API, Python, PowerShell.

## Часть 2. Отказоустойчивость

### 4. Сайт, который переживает падение сервера

**Проблема.** Витрина на одном VPS: упал хост, лёг канал, сломался деплой - сайт
недоступен. «У нас есть бэкап» не считается: бэкап, который не восстанавливали, - гипотеза.

**Что сделал.** Два независимых уровня защиты, оба автоматизированы:

- **Статический снапшот**: скрипт забирает отрендеренную витрину, добавляет баннер
  «резервный режим», `noindex` и защиту форм, проверяет целостность и пишет манифест.
  Резерв не собирается из исходников - поэтому не зависит от прода.
- **Два варианта снапшота под разные риски**: `reserve` (noindex + `Disallow: /`) - для
  переключения DNS, чтобы копия не конкурировала с основным сайтом в индексе; `public`
  (без noindex) - для локального фолбэка на том же домене, где `robots.txt` живой.
- **Локальный фолбэк**: `error_page 502/503/504` → снапшот, чтобы падение приложения
  не превращалось в белый экран.
- **Переключение DNS** через API с проверкой здоровья, **dry-run по умолчанию** и логом.
- **Холодный релей**: ВМ поднимается по API, идемпотентно, с выкладкой снапшота и сертификата.
- **Сторож доступности**: метрики в Prometheus, алерт через Alertmanager.

**Результат.** Учение: 47 страниц и 26 ассетов в снапшоте, резерв готов к публикации.
Оно же нашло блокер - у сервисного аккаунта не было роли на запуск ВМ, релей не поднялся.
Отчёт стал списком конкретных действий владельца вместо «что-то пошло не так».
Сторож отработал 168 проверок подряд без ложных переключений.

**Почему это важно:** различие «резерв есть» и «резерв проверен» - то, на чём валятся
настоящие аварии.

**Стек:** Python, nginx, API Cloudflare, Yandex Cloud API, Prometheus, Alertmanager, systemd.

## Часть 3. Инфраструктура и миграции

### 5. Миграция 90 Windows-серверов и SQL без простоя

**Контекст.** 90 Windows Server 2008-2019, включая SQL Server. Часть систем
эксплуатировалась годами без обновлений, часть держала процессы, которые останавливать
нельзя: склад, ВЭД, обмен с контрагентами.

**Что сделал.**

- Провёл волну миграций 2008 → 2016/2019 и SQL 2012/2014 → 2016 SP3.
- Сначала инвентаризация и карта зависимостей: что с чем связано, что сломается
  при обновлении, что вообще можно вывести из эксплуатации.
- Окна согласовывал с бизнесом и ИБ, на каждое изменение - бэкап и регламент отката.
- Выводил устаревшие системы, а не тащил их дальше: миграция это не только «обновить»,
  но и «убрать лишнее».

**Результат.** Парк обновлён без простоя бизнеса; появился регламент, по которому
следующая миграция - процедура, а не подвиг.

**Стек:** Windows Server, SQL Server, PowerShell/WinRM, бэкапы и восстановление.

### 6. 43 Linux-хоста под управлением Ansible

**Контекст.** Парк Linux-хостов на REDOS 8 рос стихийно: у каждого свои настройки,
свои версии пакетов, свой способ подключения. Любая проверка превращалась в обход
43 машин вручную.

**Что сделал.**

- Перевёл хосты под Ansible: роли, плейбуки, инвентарь, идемпотентные прогоны.
- SSH по CA-сертификатам вместо раздачи ключей: доступ управляется, а не «у кого-то
  остался старый ключ».
- Единый базовый профиль хоста: `chrony`, `auditd`, `zabbix-agent`, `nginx` - одинаково
  на всех, обновляется одной командой.
- `fail2ban` на 39 хостах с метриками и алертами: не просто установлен, а наблюдаем.

**Результат.** 43 хоста в управлении; новая машина приводится к стандарту ролью,
а не инструкцией на память.

**Стек:** Ansible, REDOS 8, nginx, fail2ban, Zabbix.

### 7. Proxmox → VMware: перенос виртуальных машин без простоя

**Контекст.** Смена платформы виртуализации - мероприятие, где легко потерять сутки
на согласованиях и ещё сутки на неожиданностях.

**Что сделал.**

- Спланировал перенос по группам ВМ, с приоритетом по критичности.
- Согласовал окна, на каждую группу - бэкап и план возврата.
- Перенёс без простоя бизнеса, проверяя после каждого шага, что сервисы отвечают.

**Результат.** Платформа заменена без остановки работы; появилась процедура
на случай следующей смены платформы.

**Стек:** ProxMox, VMware, бэкапы, мониторинг после переключения.

## Часть 4. Публикация сервисов и безопасность

### 8. Публикация корпоративных сервисов: nginx, WAF, DMZ

**Контекст.** Внутренние системы (корпоративная почта, файлы, ЭДО, офисный пакет)
должны быть доступны снаружи - но только через контролируемый контур.

**Что сделал.**

- Схема публикации: цепочка reverse-proxy, WAF, DMZ: снаружи виден только nginx,
  внутрь напрямую ничего не смотрит.
- Публикация Р7 Корпоративный сервер: сертификаты, интеграция с AD и почтой,
  связка с ЭДО.
- ЭДО «Етран»: прокси-контур, контроль доступности, обмен с контрагентами.
- Контроль сроков действия сертификатов и паролей учётных записей: дашборд
  и ежедневный отчёт, а не «вспомнили, когда отвалилось».

**Результат.** Сервисы доступны снаружи и при этом не выставлены в интернет напрямую.

**Стек:** nginx, WAF, DMZ, AD, сертификаты, ЭДО.

### 9. Замечания ИБ как инженерная задача

**Контекст.** Проверки ИБ приносят список замечаний, и типичная реакция - закрыть
отпиской. Через год приходит та же проверка с тем же списком.

**Что сделал.**

- Telnet и SSHv2 на терминальных серверах: разобрал вместе с вендором и парком ТСД -
  не «выключить и забыть», а перевести парк на поддерживаемый протокол.
- Слабые пароли сервисных учётных записей: прошёл по парку, перевёл на управляемые
  учётки, добавил контроль сроков (PSO в AD, дашборд и ежедневный отчёт).
- Внедрил 4-уровневую модель администрирования AD: аудит и реестр групп, чтобы права
  были видны, а не «у кого-то когда-то были».

**Результат.** Замечания закрыты по существу, а не отпиской; появился обзор прав,
который можно показать проверяющему.

**Стек:** Active Directory, LDAPS, Kerberos, PSO, PowerShell, отчётность.

### 10. Импортозамещение: REDOS 8 и выбор между Nextcloud и Р7-Офис

**Контекст.** Требование перейти на отечественное ПО. Обычная ошибка - поставить
первое, что назвали, и потом объяснять, почему не работает.

**Что сделал.**

- Перевод инфраструктуры на REDOS 8: инвентаризация, базовый профиль (Ansible),
  43 хоста под управлением.
- Замена SharePoint: провёл **пилот Nextcloud** (AD/LDAPS, файлы и версии, Talk, OCR)
  и сравнил с Р7-Офис по критериям, которые важны бизнесу, а не вендору.
- Обосновал выбор в пользу Р7; миграция выполняется на этой платформе.

**Результат.** Выбор не «по привычке», а с пилотом и аргументами; переход идёт
без сюрпризов, потому что сравнивали заранее.

**Стек:** REDOS 8, Nextcloud, Р7-Офис, AD/LDAPS, Ansible.

### 11. CI/CD и секреты: пайплайны, которые не публикуют лишнего

**Контекст.** Пайплайн, который собирает и выкладывает, обычно пишут быстро.
Пайплайн, который при этом не выкладывает секреты, - уже редкость.

**Что сделал.**

- GitLab CI: пайплайны с артефактами и отчётами, ручное подтверждение перед продом:
  автоматизация, в которой человек остаётся в контуре решения.
- Secret Detection (gitleaks) в пайплайне плюс собственный pre-commit-сканер: секрет
  ловится до коммита, а не после инцидента.
- Docker: Compose-стеки и Swarm для сервисов.

**Результат.** Деплой воспроизводим, прод трогается осознанно, а секреты не уезжают
в историю репозитория.

**Стек:** GitLab CI/CD, gitleaks, Docker Compose/Swarm, Bash.

**Контекст.** Пять лет руководил ИТ-отделом: сервисы, бюджет, проекты, люди.

**Что сделал.**

компьютеры».

**Стек:** ServiceNow, CLIO, бюджетирование, управление сервисами.

## Что это всё показывает

- Метрика без честного определения - имитация наблюдаемости.
- Резерв, который не проверяли, - гипотеза, а не отказоустойчивость.
- Миграция - это карта зависимостей и регламент отката, а не «щёлкнуть обновление».
- Интеграции ценны бизнесу не «API», а тем, что заявки не теряются.
- Импортозамещение с пилотом и сравнением дешевле, чем замена «потому что сказали».
- Баг в общем слое чинится один раз - если найти его в общем слое.
