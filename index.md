## 1. Мониторинг, которого не было: 8 дней без заявок

**Проблема.** Приём заявок на сайте агентства сломался. Заметили через **восемь дней**:
заявок не было, и отличить «нет трафика» от «сломан приём» было нечем. Метрики
«сколько дней с последней заявки» не существовало - значит, и алерта быть не могло.

**Что сделал.**

- Сначала измерение, потом алерт: скрипт ходит в API CRM, считает состояние воронки
  (последний лид, открытые задачи, активность порталов) и публикует метрики в Pushgateway.
- Prometheus скрейпит их, правила лежат в `rules.yml`, применяются перезагрузкой
  через `POST /-/reload`.
- Алерты: «нет новых лидов > 3 дней, `for: 1h`» и отдельный критический порог.
- Отдельно разобрал ловушку с метрикой: счётчик нетронутых лидов построен на `modifiedAt`,
  а наши же действия (назначение ответственного, задачи) двигают дату - метрика занижает.
  Честный признак «работа не идёт» - задачи: открытые > 0 при начатых = 0. Это записано
  в комментарии к правилам, чтобы через полгода никто не поверил метрике на слово.

**Результат.** Авария класса «приём заявок мёртв» видна через час, а не через неделю.

**Стек:** Python, Prometheus, Pushgateway, Alertmanager, CRM API.

## 2. Сайт, который переживает падение сервера

**Проблема.** Витрина на одном VPS: упал хост, лёг канал, сломался деплой - сайт недоступен.
«У нас есть бэкап» не считается: бэкап, который не восстанавливали, - это гипотеза.

**Что сделал.** Два независимых уровня защиты, оба автоматизированы:

- **Статический снапшот**: скрипт забирает отрендеренную витрину, добавляет баннер
  «резервный режим», `noindex` и защиту форм, проверяет целостность и пишет манифест.
  Резерв не собирается из исходников - поэтому не зависит от прода.
- **Два варианта снапшота под разные риски**: `reserve` (noindex + `Disallow: /`) - для
  переключения DNS, чтобы копия не конкурировала с основным сайтом в индексе; `public`
  (без noindex) - для локального фолбэка на том же домене, где `robots.txt` живой
  и `noindex` выкинул бы реальные адреса из поиска.
- **Локальный фолбэк**: `error_page 502/503/504` → снапшот, чтобы падение приложения
  не превращалось в белый экран.
- **Переключение DNS** через API с проверкой здоровья, **dry-run по умолчанию** и логом.
- **Холодный релей**: ВМ поднимается по API, идемпотентно, с выкладкой снапшота и сертификата.
- **Сторож доступности**: метрики в Prometheus, алерт через Alertmanager.

**Результат.** Учение: 47 страниц и 26 ассетов в снапшоте, резерв готов к публикации.
Учение же и нашло блокер - у сервисного аккаунта не было роли на запуск ВМ, релей
не поднялся. Это записано в отчёт с конкретными действиями владельца, а не «что-то
пошло не так». Сторож с тех пор отработал 168 успешных проверок подряд без единого
ложного переключения.

**Почему это важно:** различие «резерв есть» и «резерв проверен» - то, на чём валятся
настоящие аварии. Учение, которое нашло проблему заранее, ценнее учения, которое
прошло гладко.

**Стек:** Python, nginx, API Cloudflare, Yandex Cloud API, Prometheus, Alertmanager, systemd.

## 3. Заявки и каталог без ручного переноса

**Проблема.** Заявки приходили из трёх мест - формы сайта, телефония, порталы - и жили
по разным углам: часть в почте, часть в мессенджерах, часть «сейчас перепишу руками».
Руками теряется всегда одно и то же. Каталог новостроек обновлялся отдельно от CRM,
и менеджер называл цены по памяти.

**Что сделал.**

- **Единая точка приёма**: сайт отправляет заявки вебхуком, телефония - на защищённый
  путь с секретом. Отдельный роутер reverse-proxy отправляет `/hooks/*` на мост,
  который эти пути обслуживает - иначе путь попадал в catch-all и молча уходил не туда.
- **Секрет как условие, а не как формальность**: запрос без секрета получает `401`;
  это же и health-check «путь жив и правильно подключён».
- **Запись в CRM через API**: заявка создаётся сущностью «Лид» с источником и ответственным,
  история не теряется.
- **Синхронизация каталога и цен**: каталог выгружается и сверяется с CRM, менеджер видит
  актуальные цены, а не вчерашние.
- **Отчётность**: утренняя сводка «что требует действия / что не так с качеством данных»
  и метрики воронки - те самые, на которых построены алерты из кейса 1.

**Результат.** Заявки с сайта и звонки попадают в CRM без ручного переноса; сайт, CRM
и менеджер видят один и тот же каталог и цены.

**Стек:** Python, EspoCRM API, вебхуки, Traefik, nginx, SQL.

## 4. Один шаблон мониторинга врал про 90 серверов

**Проблема.** В системе мониторинга на 137 хостов обнаружилась системная ошибка шаблона:
90 Windows-хостов отдавали **неверные события**. Алерты формально работали, а сигнал был
ложным - худший вариант: не тишина, а уверенность в том, что всё под контролем.

**Что сделал.**

- Нашёл причину на уровне шаблона, а не отдельных хостов - значит, починил один раз,
  а не 90 раз.
- Исправил и прогнал проверку по всему парку: события стали соответствовать реальному
  состоянию.
- Выстроил гигиену вокруг: базовый профиль хоста через Ansible (chrony, auditd,
  zabbix-agent, nginx), единые политики на 43 Linux-хостах, fail2ban с метриками
  и алертами на 39 хостах.
- Алертинг на неудачные SSH-входы и блокировки fail2ban по всему парку - с работой над
  ложными срабатываниями, а не «включил и забыл».

**Результат.** Мониторинг перестал врать; изменение в общем слое масштабируется на весь
парк вместо 90 ручных правок.

**Стек:** Zabbix 7.x (шаблоны, LLD, API), Ansible, Linux (REDOS 8), Windows Server,
PowerShell/Bash.

## Что это показывает

- Метрика без честного определения - имитация наблюдаемости.
- Резерв, который не проверяли, - гипотеза, а не отказоустойчивость.
- Интеграции ценны бизнесу не «API», а тем, что заявки не теряются.
- Баг в общем слое чинится один раз - если найти его в общем слое.

Технологии в кейсах: Python, Linux, Docker, Ansible, nginx, Traefik, Prometheus, Grafana,
Loki, Zabbix, Alertmanager, GitLab CI/CD, Cloudflare API, Yandex Cloud API, EspoCRM.
